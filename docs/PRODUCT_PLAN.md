# プロダクト計画

## 結論

ハッカソンでは「正確なリアルタイム在庫サービス」を目指さない。ベンダーの非公開在庫データがなくても検証できる、次の一連の体験を完成させる。

1. ユーザーが欲しい商品を選ぶ
2. 自販機の直近の観測状況を見る
3. 売り切れなら、買えそうな近隣機へ移動する
4. 買えなかった／買えた状況を投稿する
5. ベンダーが集約された未充足需要と補充候補を見る

このループが、画像で検討された「買えなかった体験の可視化」をユーザー価値と事業者価値の両方につなぐ最短経路になる。

## 誰の、どの課題か

### ユーザー

イベント会場など混雑・需要変動が大きい場所で、特定の飲み物が欲しい人。売り切れに遭遇すると、別の自販機やコンビニを探す時間と心理的負担が発生する。

### ベンダー・施設運営者

販売成立データは持っていても「欲しかったが買えなかった」件数は通常の売上データに残らない。そのため、一時的な需要急増、欠品による逸失、商品構成の改善余地が見えづらい。

## 検証する仮説

> 売り切れに遭遇した利用者は、30秒以下かつ即時の代替案内が得られるなら状況を投稿する。集約された投稿は、イベント時の補充判断に使える需要シグナルになる。

### ユーザー側の成功指標

- 投稿開始から完了まで中央値30秒以下
- 売り切れ閲覧者の代替候補クリック率30%以上
- 投稿開始者の完了率50%以上
- 「次回も使いたい」回答60%以上

### ベンダー側の成功指標

- 補充判断に使えそうと答える担当者が3名中2名以上
- 欠品投稿上位と、実際の補充・販売データの上位が一致する
- 誤情報率15%以下（現地確認または販売データとの比較）

## MVPの機能

### P0 — デモ成立に必須

- 商品検索・選択
- 自販機マップと状況表示
- 最終確認時刻
- 正面写真の投稿と、解析候補の確認・修正・公開モック
- 選択式の買えなかった体験入力
- 同一商品を扱う近隣機の案内
- 欠品投稿の集計と補充ランキング

### P1 — 時間が残れば

- 自販機・商品の新規登録申請
- 写真添付（認識ではなく証跡として保存）
- 同一地点の複数投稿による信頼度
- イベント名・時間帯別の絞り込み
- Supabase Authによる匿名セッション

### Non-goals — ハッカソン後

- 商品画像からのSKU自動判定
- 発注や補充作業の自動実行
- 金銭価値のあるポイント
- 全自販機会社を横断したリアルタイム在庫保証
- 個人の購買行動予測

## データ獲得の現実解

最初から全国の自販機データを集めない。検証場所をイベント会場など1施設に限定し、次の順序で広げる。

1. デモでは運営側が4〜10台と主要商品を事前登録
2. 当日はQRコードを各自販機に仮設し、機械IDを確実に特定
3. 投稿から欠品・在庫ありの観測を取得
4. 施設またはベンダーから補充実績を受領し、投稿との相関を検証
5. 価値が出た後にベンダー在庫APIまたはCSV連携を交渉

## 収益化の順序

ユーザー課金より、施設・ベンダー向けの実証実験が先。初期はイベント単位の需要レポート、次に多拠点ダッシュボード、最後に補充最適化や商品構成提案へ進む。

投稿者への還元は、まずデモ内ポイントや施設クーポンで検証する。現金同等物は不正投稿対策、会計、規約対応が増えるためMVPから外す。

## 最大のリスク

| リスク | MVPでの扱い |
| --- | --- |
| 投稿が集まらない | QR導線、2択投稿、代替案内を即時リターンにする |
| 誤投稿・連投 | 端末単位の頻度制限、複数投稿の一致度、ベンダーデータ優先 |
| 在庫保証と誤認される | 「最終確認」「買える可能性」と表記し、保証表現を避ける |
| 自販機・商品マスターがない | 対象施設を限定して事前登録する |
| ベンダーに価値がない | 補充実績と突き合わせ、上位需要の一致を検証する |
