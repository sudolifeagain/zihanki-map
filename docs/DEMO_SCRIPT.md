# 3分デモ台本

## 0:00–0:30 — 課題

「イベント会場で水が欲しい。でも目の前の自販機は売り切れ。売れた商品はデータに残りますが、欲しかったのに買えなかった需要は残りません。」

## 0:30–1:20 — ユーザー体験

1. マップで「水」を選ぶ
2. 東展示棟が売り切れ、6分前の確認と表示される
3. 最寄りの「会議棟 2Fロビー」に在庫あり報告があることを見る
4. 元の機械へ戻り「今の状況を投稿する」から「売り切れていた」を選ぶ
5. +10pt と、投稿が即時反映されることを見せる

伝えること: 「在庫保証」ではなく、時刻付きのコミュニティ観測である。

## 1:20–2:20 — ベンダー体験

1. ヘッダーの「ベンダー分析」を開く
2. 買えなかった投稿と推定取りこぼし売上を見る
3. 補充候補ランキングで、場所と商品を特定できることを示す
4. 「東展示棟へ水を+10本」という次の行動までつながることを示す

伝えること: 売上データだけでは見えない未充足需要を、補充判断へ変えている。

## 2:20–3:00 — 現実性と次の検証

「今回は4台のデモデータです。実証ではイベント会場の10台にQRを置き、投稿と実際の補充・販売データを突き合わせます。検証するのは、投稿が集まるか、代替案内が使われるか、欠品投稿上位が本当の補充優先度と一致するかの3点です。」

## 想定質問

### 在庫は本当に正しいのか

在庫保証はしない。最終確認時刻と信頼度を表示し、古い投稿は「未確認」へ戻す。ベンダーデータ連携後はそちらを優先する。

### なぜユーザーが投稿するのか

投稿直後に代替候補を得られることが一次的な対価。ポイントは補助であり、ハッカソンでは金銭価値を持たせない。

### AIはどこか

初期はデータ不足なのでルールベースが正しい。投稿、販売、補充、天候、来場者データが貯まった後に需要予測へ進む。AIを使うことより、学習可能な「買えなかった」データを作ることが先。

### 写真認識はしないのか

商品名の手動選択の方が速く、誤認識を避けられる。写真は将来、証跡と新商品候補の抽出に使う。
