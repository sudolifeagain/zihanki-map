# 要件定義・ビジネス検討記録

## この文書の位置づけ

2026年8月26日に共有された6枚のビジネス検討資料と、その後に会話で確定したハッカソン向けモック要件を統合した記録である。

- 「原資料の内容」は、検討の背景と選択肢を残すための記録
- 「確定要件」は、現在のモックで採用した仕様
- 両者が異なる場合は、後から確定した要件を優先
- 未実装の内容は、対象外またはGitHub Issueとして明示

## 1. 原資料にあったビジネス要件

### 1.1 解決したい課題

中心となる課題は、次の情報が必要なときに取得しづらいことである。

- 自動販売機の商品ラインナップ
- 商品ごとの欠品状況
- 次回の搬入・補充予定

特に、イベント会場、会議施設、テーマパークなど、人が多く集まり通常時より需要が変動する場所を想定する。利用者は単に飲み物が欲しいだけでなく、「特定の銘柄を今飲みたい」という状況にある。

### 1.2 利用者に発生する負担

欲しい商品がない場合、利用者は購入を諦めるか、別の自販機やコンビニを探す。

| 負担 | 原資料での整理 |
| --- | --- |
| 時間 | 別の自販機・コンビニまでの距離に左右される |
| 金銭 | 飲み物1本分、100円程度からの機会損失感 |
| 心理 | 見つからなかった落胆、別の場所を探すわずらわしさ |
| 手間 | どこに在庫があるか分からないまま現地を回る必要がある |

混雑するイベントほど「買えなかった」体験の発生確率が上がるため、期間全体では潜在的に大きな課題になり得る。一方、通常時の販売体制はすでに一定程度最適化されており、需要が急増する場面に対象を絞るべきという仮説が置かれていた。

### 1.3 現在の方法と限界

原資料では、現在の確認手段を次のように整理していた。

- 実際に自販機まで行き、商品があるか目視する
- コンビニ等であれば電話確認も可能だが、利用者にとってハードルが高い

このままでは、次の影響が残る。

#### 顧客側

- 自販機での購入率が下がり、コンビニ等へ流れる
- 購入体験の満足度が上がらない
- 特定の銘柄を探すための移動が発生する

#### ベンダー・施設側

- 欠品による拡張可能だった売上を獲得できない
- 売買が成立していないため、通常の販売データでは逸失利益を把握できない
- 通常時の販売実績だけでは、イベント固有の潜在需要を把握しにくい

### 1.4 原因仮説

| 原因 | 補足 | 継続性 |
| --- | --- | --- |
| 予測を上回る需要 | 人が集まるイベント時に発生しやすい | 特定イベントで再発 |
| 購入データが不十分 | 成立した購入は残るが、買えなかったケースは残らない | 継続的 |
| 欠品を現地でしか確認できない | ベンダーは把握できても、一般利用者へ届いていない | 連携で改善可能 |
| データが分散 | 売上、在庫、天候、来場者などが別々に存在 | 統合が必要 |

原資料では、ハッカソンで最初に解消する原因を「買えなかった体験の可視化」としていた。

### 1.5 原資料にあった解決案

1. 利用者が自販機の写真を投稿し、商品ラインナップと欠品状況を更新する
2. 「何が欲しかったか」を含む買えなかった体験を投稿する
3. 投稿の動機としてポイントを付与する
4. 欲しい商品が売り切れなら、近くで在庫がありそうな自販機を案内する
5. 商品名を基準に、状態と最終確認時刻を表示する
6. 新商品・未登録商品を利用者がタグ付け・分類できるようにする
7. 集まった未充足需要を分析し、「この自販機へ水を10本追加」などの補充・品揃えを提案する

想定されていたデータ価値は、次のとおり。

- 売上だけでは見えない逸失した購買意欲
- 銘柄ごとの検索回数・需要トレンド
- 欠品後に別の場所へ移動したか、購入を諦めたかという行動
- ベンダーや施設が補充・商品構成を改善するための材料

個人単位の購買過程予測は将来案として挙がっていたが、現在は匿名集計で価値を検証することを優先する。

### 1.6 原資料で定義されたMVPの核

原資料の最小機能は、次の一文に集約されていた。

> 買えない体験を減らし、買いたいものを買える体験を増やす。

現在のモックでは、これを「写真から得た観測情報で、欲しい銘柄が買えそうな場所を案内し、買えなかった需要を補充候補へ変える」と具体化している。

## 2. 現在の確定要件

### 2.1 対象と前提

- 主画面は地図
- サンプル地域は東京ビッグサイト周辺
- 自販機は運営側が登録した4台のサンプルのみ
- 自販機・設置位置・在庫はデモデータ
- 写真と銘柄は実在のものを使用するが、デモピンの実機を示すものではない
- 投稿者はログイン不要の匿名ユーザー
- 投稿と体験データはブラウザ内のlocalStorageに保存
- インフラはCloudflare Workers Static Assets
- 画像AIは動作させず、解析体験のみをモックする

### 2.2 利用者向け機能要件

| ID | 要件 | 現在の状態 |
| --- | --- | --- |
| FR-01 | 東京ビッグサイト周辺のサンプル地図を主画面として表示する | 実装済み |
| FR-02 | 登録済み自販機をマーカーで表示する | 実装済み |
| FR-03 | 場所と飲みたい銘柄を指定できる | UI実装済み。場所検索は演出のみ |
| FR-04 | 銘柄ごとに在庫あり、残りわずか、売り切れ、未確認を色と文字で表示する | 実装済み |
| FR-05 | 自販機名、ランドマーク、距離、最終確認時刻を表示する | 実装済み |
| FR-06 | 売り切れ時に、同じ銘柄が買えそうな近隣自販機を案内する | 実装済み |
| FR-07 | 登録済み自販機を選び、正面写真1枚を投稿できる | モック実装済み |
| FR-08 | 写真の解析中表示を経て、全商品の銘柄・状態候補を表示する | モック実装済み |
| FR-09 | AI候補は自動公開せず、投稿者が状態を確認・修正して公開する | 実装済み |
| FR-10 | 写真は端末内でのみプレビューし、モックでは外部送信しない | 実装済み |
| FR-11 | 買えなかった体験は任意入力とする | 実装済み |
| FR-12 | 買えなかった体験は自由記述ではなく選択式にする | 実装済み |
| FR-13 | 投稿後、対象自販機の状態と最終確認時刻を即時更新する | 実装済み |
| FR-14 | 投稿のデモ報酬として10ポイントを加算する | 実装済み |

### 2.3 買えなかった体験の入力項目

| 項目 | 選択肢 |
| --- | --- |
| 欲しかった銘柄 | 解析候補または登録済み商品から選択 |
| 買えなかった理由 | 売り切れランプ、ラインナップになかった、決済できなかった |
| その後の行動 | 別の自販機、コンビニ、別商品を購入、購入を断念 |

自由記述を使わないことで入力時間を短縮し、ベンダー画面で直接集計できるデータにする。

### 2.4 ベンダー向け機能要件

| ID | 要件 | 現在の状態 |
| --- | --- | --- |
| FR-20 | 買えなかった投稿数を表示する | 実装済み |
| FR-21 | 欠品投稿から推定取りこぼし売上を表示する | デモ係数で実装済み |
| FR-22 | 場所・銘柄別の補充優先度を表示する | 実装済み |
| FR-23 | 補充本数・品揃えの次アクションを提示する | ルールベースのデモ |
| FR-24 | 検索回数・期間・イベント別の需要トレンドを表示する | 未実装 |
| FR-25 | 次回の補充・搬入予定を利用者へ表示する | 未実装 |

### 2.5 非機能要件

- モバイルファーストかつデスクトップでも利用できる
- 在庫保証ではなく、時刻付きの観測情報として表現する
- 実在データとの誤認を避けるため「デモデータ」「AI解析モック」を常時明示する
- 写真の撮影地とデモピンが一致しないことを明記する
- OpenStreetMapの帰属表示を地図上から隠さない
- 公開リポジトリに認証情報を含めない
- ビルドとドメインテストがGitHub Actionsで成功する
- Cloudflareの公開URLからHTTPSで利用できる

## 3. モックの対象外

次は意図的にモックから外している。

- 実際の画像AI推論
- 写真のサーバー保存
- 複数端末間の投稿共有
- 自販機会社のリアルタイム在庫API
- 一般ユーザーによる新規自販機登録
- 正確な経路案内と屋内階層ナビゲーション
- 金銭価値のあるポイント
- 発注・補充作業の自動実行
- 個人を追跡する購買行動予測

## 5. 検証指標

### 利用者価値

- 写真投稿開始から公開までの中央値が30秒以下
- 投稿開始者の完了率が50%以上
- 売り切れ表示を見た利用者の代替候補クリック率が30%以上
- 買えなかった体験の任意入力率が30%以上
- 誤った状態表示の割合が15%以下

### ベンダー価値

- 担当者3名中2名以上が補充判断に利用できそうと評価
- 欠品投稿上位と実際の補充・販売データ上位が一致
- 欠品から補充までの時間を比較できる
- 「別の場所で購入」「購入断念」の割合を算出できる
